# Etapa 4b-1 — Criptografia ponta a ponta (núcleo)

> Resolve o item **F** do [`01-baseline-seguranca.md`](01-baseline-seguranca.md):
> o servidor (e quem lê o banco) deixa de ver o conteúdo das mensagens.
> Fora do escopo: frontend e tudo o que muda a composição da sala (sair,
> remover membro, trocar a chave da sala), que é a **4b-2**.

## 1. Objetivo

Até a Etapa 4a, o TLS protegia o conteúdo **na rede**, mas o proxy, o
backend e o banco ainda viam tudo em claro
([`04-tls-e-proxy.md`](04-tls-e-proxy.md) §9). Agora:

- cada mensagem é **cifrada e assinada no cliente** antes de sair; o servidor
  recebe, guarda e entrega só um envelope opaco;
- cada sala tem uma **chave AES-256 gerada no cliente** do criador, que chega
  a cada membro **embrulhada** (wrap) para a chave pública dele — o servidor
  guarda os wraps, mas não consegue abri-los;
- as chaves privadas de cada usuário **nunca saem do cliente**: ficam num
  keystore cifrado com uma senha de cifragem, diferente da senha de login;
- o receptor **verifica a assinatura** de cada mensagem com a chave do
  remetente que ele próprio fixou (TOFU), e pode conferir essa chave
  comparando um **número de segurança** com a outra pessoa.

O servidor continua decidindo **quem** é membro e roteando as mensagens
(metadados), mas, sem as chaves privadas, não lê nem forja conteúdo.

Onde está o quê:

| Parte | Onde |
|---|---|
| Núcleo criptográfico (isomórfico: Node e navegador, só Web Crypto) | `shared/e2ee/` (`index.js`, `identity.js`, `roomKeys.js`, `messages.js`, `keystore.js`, `trust.js`, `receiver.js`) |
| Adaptador Node (arquivos do keystore, permissões) | `shared/e2ee/node.js` |
| Diretório de chaves públicas | `backend/routes/keys.js` |
| Versões e wraps da chave da sala | `backend/routes/roomKeys.js` |
| Falha fechada do `MSG_SEND` (estrutura do envelope) | `backend/realtime/envelope.js`, `realtime/handlers.js` |
| Cliente de referência com E2EE | `backend/tools/ws-client.js`, `backend/tools/e2ee-session.js` |
| Prova contra a stack no ar | `scripts/verify-e2ee.sh` |

## 2. Modelo de ameaças da E2EE

Atores do [`00-modelo-ameacas.md`](00-modelo-ameacas.md), agora com E2EE:

| Ataque | Quem | Controle | Prova |
|---|---|---|---|
| Ler o conteúdo no banco ou num backup | admin, acesso ao banco | só o envelope cifrado é gravado; `CHECK` de formato na coluna | `e2eeMessages.test.js` ("o marcador não aparece…"), `verify-e2ee.sh` (a) e (c) |
| Ler o conteúdo no proxy/backend (onde o TLS termina) | admin do servidor | o corpo já chega cifrado do cliente | `verify-e2ee.sh` (captura da rede interna) |
| Obter a chave da sala pelo servidor | admin | a chave só existe embrulhada para a chave ECDH de cada membro | `roomKeys.test.js` ("nenhuma coluna … contém a chave da sala") |
| Trocar o remetente (`from`) de uma mensagem | servidor malicioso | AAD com o `senderId` + assinatura ECDSA verificada com a chave **fixada** | `e2eeMessages.test.js` ("servidor troca o `from`…") |
| Adulterar texto cifrado, IV, sala, `cid` ou versão | servidor, rede | AES-GCM (tag) + assinatura sobre AAD‖iv‖ct | `crypto.test.js` |
| Reentregar mensagem antiga (outro `id`) | servidor | o cliente ignora (remetente, `cid`) já aceitos | `e2eeMessages.test.js` ("reentrega…") |
| Entregar a um novato uma chave de sala falsa | membro malicioso | compromisso da chave assinado pelo criador; o novato descarta e pede outra | `roomKeys.test.js` ("compromisso da chave…") |
| Inserir um "membro fantasma" para receber a chave | admin (controla `rooms_users`) | sem entrega automática a quem não foi verificado: precisa de `/approve` | `wsClientE2ee.test.js` ("membro fantasma") |
| Trocar a chave pública de um usuário (MITM) | admin | TOFU: chave diferente da fixada → **CHAVE ALTERADA**, recusa wrap e mensagens até `/safety` + `/trust` | `wsClientE2ee.test.js` ("CHAVE ALTERADA…") |
| Apresentar outro "criador" ou versão menor da chave da sala | servidor | criador e maior versão fixados por sala no keystore | `wsClientE2ee.test.js` ("criador da sala é fixado") |
| Mandar texto puro por engano (cliente com bug) | — | falha fechada no servidor (`E2EE_REQUIRED`) e no banco (`CHECK`) | `e2eeMessages.test.js`, mutação `no-encrypt` do `verify-e2ee.sh` |
| Roubar o keystore do disco | quem acessa a máquina | AES-GCM com chave de PBKDF2 (600 000 iterações); arquivo 0600 fora de repositórios | `keystore.test.js` |
| Injetar sequências de escape no terminal | outro usuário, servidor | toda linha impressa com os caracteres de controle visíveis | `wsClientE2ee.test.js` ("sequências de escape") |

**Fora do que a E2EE protege** (detalhes na §10): metadados (quem fala com
quem, quando, tamanho aproximado), disponibilidade (o servidor pode
omitir, atrasar ou reordenar mensagens), o próprio dispositivo do usuário e
a primeira troca de chaves quando o número de segurança não é conferido.
